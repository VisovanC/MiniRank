MiniRank — Build Process Log

Keyword position tracker (assessment). This file is updated at the end of each M-milestone (M1–M8) and after any major change, so the whole build is explicit and easy to follow. Both the human and the AI edit this file.

Plan

Scope & stack

  • Plain PHP 8 (no framework), PDO + SQLite, vanilla HTML/CSS/JS, one fetch()-driven AJAX refresh.
  • Single user, single website, no login for M1–M8. Multi-project / accounts are stretch goals the schema must not block.
  • M1–M8 in order; repo is committed after each milestone.

Key decisions

  • Controllers vs. lib split: thin controllers (request/response, read superglobals, echo) vs. lib/ pure functions (take data as arguments, never touch superglobals, never echo). Keeps core logic unit-testable later with an in-memory SQLite PDO.
  • Document root: public/ served with php -S localhost:8000 -t public.
  • Routing: plain PHP files as endpoints (3 routes). A front controller can replace them later without touching lib/.
  • Refresh endpoint: public/refresh.php, POST-only, returns JSON.
  • Bootstrap choke point: every entry file requires lib/bootstrap.php — the future home of session/auth/CSRF hooks.
  • Decided 2026-08-17: trend rule = compare latest vs. 7 days earlier with ±1-rank tolerance (a 1-rank move is "stable"); refresh = upsert today's row (idempotent); edit = rename only (history kept), delete = hard delete + cascade; run target = Docker Compose (php:8.2); UI copy = English; keyword search = case-insensitive via SQLite default LIKE (ASCII fold — fine for English keywords; non-ASCII folding intentionally out of scope).

SQLite schema (proposed)

CREATE TABLE IF NOT EXISTS keywords (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  phrase     TEXT    NOT NULL UNIQUE,
  created_at TEXT    NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS positions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  keyword_id INTEGER NOT NULL REFERENCES keywords(id) ON DELETE CASCADE,
  date       TEXT    NOT NULL,                       -- 'YYYY-MM-DD'
  position   INTEGER NOT NULL CHECK (position BETWEEN 1 AND 100),
  created_at TEXT    NOT NULL DEFAULT (datetime('now')),
  UNIQUE (keyword_id, date)
);

CREATE INDEX IF NOT EXISTS idx_positions_keyword_date ON positions (keyword_id, date);
CREATE INDEX IF NOT EXISTS idx_positions_date         ON positions (date);
  • UNIQUE (keyword_id, date) guarantees one position per keyword per day → makes refresh an upsert.
  • Multi-project later = add a projects table + a nullable keywords.project_id column. Today the site URL lives in config.php, so nothing blocks that.

Routing choice

Plain PHP files as endpoints, not a dispatcher: the app has only 3 routes, so a hand-rolled router is indirection without payoff. Each file is obviously a route, which suits an assessment that values clarity. When multi-project arrives, a front controller can dispatch on PATH_INFO — lib/ and the controllers don't change.

CSRF / auth hooks (stretch — slotted in, not built)

  • Every entry file starts with require lib/bootstrap.php. Later, require_auth() and a CSRF token check on POST endpoints go in right there — no rewrite.
  • refresh.php is already POST-only, so CSRF validation later covers exactly one mutation.
  • Sessions/superglobals stay in bootstrap + controllers; lib/ stays clean and testable.

Milestones

M1 — Keywords CRUD (done)

  • Built: schema + auto-init, lib/ pure functions (db, schema, keywords, escape), thin KeywordListController, public/index.php, responsive CSS, Dockerfile + compose, README.
  • Add / edit (rename, history kept) / delete (hard, cascades) / duplicate rejected via the UNIQUE constraint (caught as a constraint violation), whitespace-only rejected by trim+empty validation.
  • Security in place from day one: all queries parameterized, all output through e() (htmlspecialchars). XSS payload renders as literal text.
  • Tests: AI smoke tests over real HTTP (empty state, create, duplicate error, XSS escaping, edit form prefill, update, delete) and manual error testing by the user — duplicate rejected, whitespace-only rejected, XSS rendered literally (not executed), edit/delete work, and data survives a reload (persisted to SQLite, not in-memory).
  • Note: Docker stack files added but image not built yet (daemon was down during the session).

M2 — Seeded history (done)

  • Built: scripts/seed.php; lib/refresh.php (simulate_positions — random walk, clamped 1–100, later reused by M3); lib/positions.php (position_seed = INSERT OR IGNORE); keyword_count().
  • Idempotent by design: demo keywords inserted only when the table is empty; daily positions backfilled for every keyword (last 30 days) with INSERT OR IGNORE — re-runs add nothing.
  • Tests: AI smoke test (fresh seed 8 keywords × 30 days = 240 rows, 30 distinct days, range 1–100, re-run adds 0) and user manual checks — ran the script on a clean DB, inspected the data in DB Browser for SQLite, re-ran the script (no duplicates added), and spot-checked a keyword's full history.

M3 — Refresh simulation (done)

  • Built: lib/refresh.php (refresh_today — random-walk step from yesterday's rank, injectable rng); lib/positions.php (position_upsert via ON CONFLICT, position_before, position_last_date); RefreshController + public/refresh.php (POST-only, JSON); public/assets/js/app.js — fetch() on the "Refresh positions" button, no page reload; toolbar + status line on the list page.
  • Upsert verified: re-clicking overwrites today's row — row count and distinct days stay constant.
  • Tests: AI endpoint tests (POST → {"ok":true,"date":…,"count":9}, repeat POST idempotent, GET → 405) and user browser test of the button.
  • Incident: user saw the old page (no button, app.js 404) and suspected the template wasn't saved. Root cause: Docker bakes code in at image build time (COPY . /app) — the running container served a stale image. Fix: docker compose up -d --build. Lesson recorded in the failed-prompt slot below.

M4 — Keyword list (done)

  • Built: lib/trend.php (latest_position, trend_from_history — latest vs. 7 days earlier, ±1 tolerance, falls back to the earliest row inside the 7-day window, null when <2 data points); all_keyword_histories (single query, no N+1); text search on the list with %/_/\ escaped in the LIKE pattern; new columns Position, Trend (7d), Added; search box + Clear.
  • Trend display: ▲ Improved / ▼ Declined / ─ Stable (color-coded), "—" when no history.
  • Tests: AI HTTP tests (headers render, all three trend states present, search "seo" → 3 hits, no-match message, literal % doesn't match everything) + lib unit checks (exact-7d compare, window fallback, ±1 tolerance, null on empty/single-row history) + user browser test.

M5 — Keyword detail page (done)

  • Built: positions_for_keyword() (history query); KeywordDetailController + public/keyword.php (?id=, 404 on missing/invalid id); keyword phrases on the list now link to the detail page.
  • Detail page: current position + record count + full history table (newest first).
  • Bug found & fixed during user review (logged in the failed-prompt slot): the Refresh button updated only the status line, not the table. Fix: refresh.php returns the updated rows in JSON, app.js rewrites the cells in place; row metrics shared via keyword_rows_with_metrics() + trend_label() in lib/trend.php.
  • Tests: AI HTTP tests (history table, current position, 404 on id=9999 and missing id, phrase links) + user browser test that caught the refresh bug.

M6 — Security basics (done)

  • Audit (mostly verifying what was already in place from day one):
    • Parameterized queries: every prepare() uses bound parameters; the only dynamic SQL is the search filter, which binds the LIKE value (with %/_/\ escaped) — no SQL built by string concatenation.
    • Escaped output: every echo of user/DB data goes through e() (htmlspecialchars, ENT_QUOTES, UTF-8); all ids/positions cast to (int). Earlier XSS smoke test (payload rendered as literal text) already confirmed this.
    • No secrets: config holds only a DB path and site URL; verified via git ls-files that no .db/.sqlite/.env/data files are tracked (data/, *.db, .env in .gitignore).
  • Added hardening: X-Content-Type-Options: nosniff + X-Frame-Options: SAMEORIGIN on all responses (bootstrap choke point).
  • Tests: header check on HTML + JSON responses (nosniff/SAMEORIGIN present).
  • Note: CSRF + auth remain stretch goals (hooks reserved in bootstrap). Production would also set display_errors=off so stack traces never leak — left on for this assessment.

M7 — Runs in 5 minutes (done)

  • README rewritten around a 5-minute quick start: docker compose up -d + docker compose run --rm app php scripts/seed.php → http://localhost:8000.
  • Verified the Docker path end-to-end for the first time (daemon was down in earlier milestones): image builds (php:8.2-cli-alpine, pdo_sqlite compiled in), app serves, refresh endpoint returns JSON, seed is idempotent ("0 new" on re-run).
  • Fresh-clone flow proven with an isolated named volume: first request auto-creates the schema, seed adds 8 keywords / 240 rows, list renders. One-command start + seed is genuinely all that's needed.
  • Note: the host data/ directory couldn't be renamed for an in-place fresh test (Windows file lock on the bind mount), so the fresh flow was validated against an empty volume instead — equivalent result.

M8 — Responsive (done)

  • Below 480px: add/edit and search forms stack vertically with full-width inputs/buttons; tighter paddings.

Prompts & fixes

Four real prompts that mattered — including two that failed — and concrete AI mistakes, how they were caught, and the fix.

1. The foundation prompt (the most relevant one)

Prompt: "I'm building a keyword-position-tracker web app for an assessment. Stack: plain PHP (no framework), PDO for the DB, SQLite, vanilla HTML/CSS/JS, plain AJAX (fetch) for one dynamic refresh action… Do NOT implement anything yet… propose ONLY: 1) directory structure separating controllers from a lib/ of pure functions, 2) the SQLite schema, 3) the routing approach, 4) where CSRF/auth hooks slot in later… also create a process.html kept in three sections (Plan / Prompts & fixes / Retrospective)."

Why it mattered: this single prompt forced a plan-first session and set every architectural decision before the first line of code — the controller/lib split (testable core), the schema's UNIQUE(keyword_id, date) upsert design, plain-file routing, and the bootstrap.php choke point for future auth/CSRF. Everything since builds on these choices.

Mistakes: none in this one — planning only, no code written. (The failed prompt is logged in slot 3.)

2. The M1 build-and-review prompt

Prompt: "lets go ahead with M1 but before commiting i want to check it, so just build it and we ll commit it after i give the go ahead."

Why it mattered: established the review-before-commit workflow we now repeat every milestone — the agent builds and self-tests, the human does their own error testing, and only then do we log + commit.

Mistakes: none functional, but one test-script slip on my side — a mismatched grep pattern during smoke testing made an edit-form check look like it failed. The app was fine; re-running with the correct pattern against a clean DB proved it. Lesson: clean up between test runs and sanity-check the test itself.

3. The one that failed — the M3 stale-page report

Prompt: "index.php doesn't render the refresh button or 'Last refreshed' line, and app.js never loads per the Network tab… did the index.php template actually get updated, or did that change not get applied/saved?"

What happened: the change was saved and worked locally, but the user's Docker container kept serving the previous page. The AI's mistake: when the project chose Docker as the run target, the AI didn't flag that code is baked into the image at build time — so after every code change the user must rebuild (docker compose up -d --build), not just re-run compose.

How it was caught: the user's Network tab showed app.js 404 — impossible if the working tree were being served (the file is on disk and serves HTTP 200 locally), which pointed at a stale image rather than unsaved code.

Fix: documented rebuild workflow; future milestones will state it explicitly in the commit note.

4. The one that failed — the M5 refresh button

Prompt: "if i press the refresh positions button, nothing happens unless i refresh the web page as well"

What went wrong: the AJAX handler updated only the one-line status text. The Position/Trend cells in the table are server-rendered HTML and nothing in app.js touched them — so clicking Refresh silently changed the database but left the visible table stale until a full page reload. The fetch itself was never broken (a reload showed the new numbers), which made the bug easy to misread as "nothing happened".

How it was caught: the user pressed the button, saw no change, reloaded, and the positions were different — proof the server updated but the DOM didn't.

Fix: refresh.php now returns the refreshed rows (id, position, trend, trend_label) in the JSON; app.js rewrites each row's cells via data-keyword-id; and the row-metrics logic is shared with the list page (keyword_rows_with_metrics()) so the table and the endpoint always agree. Lesson: when an AJAX action "does nothing", check what the DOM is actually supposed to change — a hidden server-side success is not a visible result.
